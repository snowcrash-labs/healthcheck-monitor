# Persistent dashboard operations

The `serve` command collects autonomously and serves the Solid dashboard through Axum. Browser requests read a shared view and never start checks. `run`, `watch`, `report`, `diff`, configuration validation and authentication commands remain available; they do not require the dashboard's PostgreSQL database. Monitoring permissions and health semantics remain those in the [monitor runbook](2026-09-05-monitor-operations.md).

## Local demo

Use stable Rust with its prebuilt standard library, Node 24 or newer, and PostgreSQL 18.6 or newer. The checked-in frontend uses Vite 8.2.2, Solid 2.0.0-rc.6, the compatible router 2.0.0-next.21, and official compiler plugin 3.0.0-next.39. The router's stable 1.x release requires Solid 1.x; its prerelease is intentional for the requested Solid 2 RC. Dependencies are locked in `Cargo.lock` and `dashboard/package-lock.json`.

From the repository root, build the development binary and static frontend:

```sh
cargo build -p healthcheck-monitor
npm --prefix dashboard ci
npm --prefix dashboard run build
```

The local PostgreSQL databases `healthcheck_monitor_dashboard_dev` and `healthcheck_monitor_dashboard_test` were created for this project on the existing native macOS server. On another machine, provision an isolated database owned by the monitoring service role. Embedded migrations create the `health_monitor` schema on startup. Application primary keys are generated by PostgreSQL's native `uuidv7()`; the client does not allocate keys. The service role needs schema creation for migrations, then read/write/delete access to its own history tables. Provider identities remain read-only.

Start a focused demo against the explicitly configured development Kubernetes target:

```sh
env HEALTHCHECK_DATABASE_URL='postgresql:///healthcheck_monitor_dashboard_dev?host=/tmp' \
  target/debug/healthcheck-monitor serve --config monitor.toml \
  --server-config server.example.toml --target dev --check kubernetes --samples 1 \
  --output evidence/dashboard-demo
```

Open `http://127.0.0.1:9840`. Checks continue after the browser closes. Remove `--check kubernetes` to run the full configured profile, or select `--profile quick` or `--profile deep`. Missing cloud credentials appear as incomplete coverage. `--interval 60s` overrides selected cadences; `--duration 10m` ends normally after ten minutes. Ctrl-C or SIGTERM stops collection and allows five seconds for partial evidence, history and connection cleanup. Use a separate `--output` directory for concurrent one-off assessments; the evidence store enforces a single writer.

The overview separates health findings, collection coverage, observation freshness, history availability and the monitor heartbeat. Findings and resources have server-side pagination and target filters; resource detail retains original observation timestamps. History records new, worsened, recovered, stale, removed and reappeared findings. Navigation preserves the target selection. The top bar stays visible on desktop and mobile. Light, dark and system themes use centralized CSS and a persisted local preference.

One-off assessments continue through the same engine:

```sh
target/debug/healthcheck-monitor run --target dev --check queues --samples 1 --output evidence/one-off
target/debug/healthcheck-monitor run --profile full --target dev --output evidence/full-assessment
target/debug/healthcheck-monitor report evidence/one-off/monitor-latest.json
```

## TLS and access

Copy `server.example.toml` to the ignored `server.local.toml` for local changes. Paths in this file are resolved relative to the file. Enable `[tls]` with PEM certificate and private-key paths. The certificate must match the listener hostname and be trusted by the browser. TLS advertises HTTP/2 first through ALPN and retains HTTP/1.1 compatibility. Plain loopback HTTP is available for development. Listener keys and certificates are bounded to 1 MiB each; keep private keys readable only by their owner. Listener, TLS, access and history settings require a restart.

The completed local verification used a short-lived self-signed certificate under ignored `evidence/dashboard-tls`; browser trust was bypassed only in the local test context, and the OS trust store was not changed. Those test keys are not deployment assets.

Local access requires a loopback listener, loopback peer and localhost authority. Cross-site API access and all write methods are rejected. Shared access requires an authenticated reverse proxy. Configure the proxy to preserve the public Host, authenticate users, remove incoming identity/key headers, and inject its verified email plus a secret of at least 32 bytes:

```toml
[access]
mode = "proxy"
secret_env = "HEALTHCHECK_PROXY_KEY"
public_origin = "https://health.example.com"
trusted_peers = ["127.0.0.1/32", "::1/128"]
allowed_domains = ["example.com"]
```

The proxy supplies `x-auth-request-email` and `x-healthcheck-proxy-key`. All configured trusted peers must be controlled proxy addresses. The server verifies the peer, authority, secret and email domain before returning dashboard data. The minimal `/healthz` endpoint reports only the monitor heartbeat and is available without proxy identity. Credentials and provider payloads never enter frontend assets or API responses. The public origin and proxy integration must be validated before shared deployment; no proxy or deployment was created here.

Remote PostgreSQL connections require TLS with platform certificate validation. Local Unix sockets and loopback connections support the existing native server. Set `HEALTHCHECK_DATABASE_URL` through the supervisor's environment; do not put credentials in the frontend or commit them. Database errors are logged as fixed operational categories, without SQL values or connection strings.

## Bounds and persistence

The default dashboard has 64 accepted connections, 16 ordinary response slots, 16 independent event streams, a 32 MiB compact read view and a 2 MiB uncompressed JSON response limit. Slots remain held until response bodies close. TLS handshakes have a five-second deadline. Oversized responses fail explicitly; incomplete read views are marked. SSE carries coalesced revision announcements, with five-second heartbeats. The browser cancels obsolete reads, times out requests after ten seconds, reconnects streams and polls every fifteen seconds as a fallback.

PostgreSQL uses two pooled connections by default, five-second checkout/connect/query deadlines, fixed retention passes and batches of at most 256 rows per insert. Prepared-statement caching is disabled because the current driver offers no finite cache capacity. The history journal admits at most 64 batches and 16 MiB, including in-flight records. The default retention is 24 hours, 10,000 finding events, 100,000 check summaries, 1,000 gap records and 32 configuration revisions. Limits are editable and validated. Retention removes only monitor-owned rows; it does not cap PostgreSQL's WAL or physical disk allocation, which remain database operating concerns.

Database faults leave current collection and the read view available. Retries back off from one second to sixty seconds. Dropped records increment visible counters and are recorded as delivery gaps when storage recovers. Clean shutdown drains queued and in-flight work within the cleanup deadline. Forced termination or an outage extending through shutdown can lose pending database history; an operational error reports this, and disk snapshots remain the independent evidence path. The database journal is not a durable spool or an exactly-once delivery guarantee across process crashes.

The JSON/Markdown/NDJSON evidence store retains its existing atomic publication, owner-only permissions, restart recovery and disk retention. PostgreSQL stores compact transition metadata and check summaries, not full provider objects, raw logs, application database rows, secret values or queue messages. Restart recovers current comparison state from the newest valid local snapshot while preserving its original age.

## Reload and development

SIGHUP reloads `monitor.toml` atomically for both `watch` and `serve`. Invalid replacements retain the previous configuration. New views and history carry the effective revision; cached observations keep their source timestamps. Listener, database, proxy and asset settings are separate and require process restart.

For frontend iteration, keep the loopback service running without TLS and use `npm --prefix dashboard run dev`. Vite listens on `127.0.0.1:5173` and proxies `/api` to the service. Use the Axum-served static build for security-header, deep-link and HTTP/2 validation.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
env HEALTHCHECK_TEST_DATABASE_URL='postgresql:///healthcheck_monitor_dashboard_test?host=/tmp' \
  cargo test -p monitor-history --test postgres -- --include-ignored
npm --prefix dashboard run check
npm --prefix dashboard test
npm --prefix dashboard run build
env HEALTHCHECK_DASHBOARD_URL='http://127.0.0.1:9840' npm --prefix dashboard run test:browser
cargo upgrade --incompatible
cargo audit
npm --prefix dashboard audit
```

The browser test requires Playwright Chromium and a running service with at least one observed resource. Install the browser once with `npm --prefix dashboard exec -- playwright install chromium`. It checks routed/deep-linked resources, sticky headers, target selection, persisted themes, mobile navigation and disconnect/reconnect behavior. PostgreSQL tests refuse any database name other than `healthcheck_monitor_dashboard_test` and exercise retention there. No Rust release build is required.

Foreground supervision on Linux and macOS follows the [monitor runbook](2026-09-05-monitor-operations.md). Set the working directory, explicit configuration/output paths and history environment in the supervisor. Current dashboard verification is native macOS; current dashboard changes have not been rerun on Linux. Real GCP/AWS/Azure credential and telemetry-mapping gaps remain documented in the original verification record.
