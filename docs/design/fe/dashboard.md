# Dashboard frontend conventions

The dashboard uses SolidJS 2.0 RC and `@solidjs/web` for JSX and rendering, with the compatible Solid router. Global connection, target selection, current overview and refresh state live in Solid context. Effects use separate compute and apply functions; setup and cleanup use `onSettled` or returned effect cleanup. Props are read reactively inside JSX or derived computations.

All styling is in centralized CSS. Native form controls, visible focus, semantic tables and explicit empty/error states support keyboard and screen-reader use. Status colors are accompanied by text. Observation timestamps retain their source age, and a disconnected browser cannot present an apparently current green state.

Resource rows show the two highest-severity active finding summaries, total finding count, evidence age or staleness, and up to three observed facts when findings exist. The API joins findings to one bounded resource page in a single pass; the browser does not issue per-resource requests. Each summary links to the full resource detail.

Target panels open dedicated target overviews. Check counts and Checks navigation expose every configured check, its purpose, coverage and underlying operations. User-facing descriptions use typed catalogs; coverage enum names never appear as labels. Cards preview gaps with an explicit link to all operations. Required evidence, optional gaps, health and freshness remain separate.

Resource details prioritize triggering values, detection times, location and native console links. Observations are grouped by check and component with original timestamps; current metadata does not replace retained failure evidence. Operation and evidence lists reuse keyset pagination. Backend-generated console URLs are validated against approved HTTPS destinations at the browser boundary. Unknown metadata is shown as not recorded. Direct target routes and the persistent selector remain synchronized.

API responses enter as `unknown` and are validated with Zod before entering state. TypeScript enables strict checking, unchecked-index checks, exact optional properties and dependency declaration checking. Findings and resources use stable keyset pagination with automatic loading at both scroll boundaries and keyboard-accessible paging buttons. The browser retains three fifty-row pages; evicted pages can be fetched again in either direction. Search runs against the full current dataset, including observed resource facts. Obsolete requests are cancelled, refreshes preserve a visible row anchor, and neither the dashboard nor the API adds a second result-count limit to collected evidence. Event streams announce revisions rather than transferring full evidence. Refreshing a view reads current state and never launches collection. Dependencies are locked; Solid and its renderer use the requested 2.0 release candidate while other dependencies track current compatible releases.

Production serves one Rust executable. Vite runs during the build, then gzip/zstd representations are generated and embedded with `rust-embed`. The Axum asset handler borrows embedded bytes, negotiates an acceptable encoding and uses representation-specific ETags. No frontend filesystem or Node process is required at runtime. Authentication covers both the API and the embedded bundle.
